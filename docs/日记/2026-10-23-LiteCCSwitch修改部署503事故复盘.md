# Lite CC Switch 修改部署导致 503：事故复盘

## 摘要

本次工作原本是处理 Codex 流式响应断流，并尝试让 Lite 在供应商失败时自动切换。为部署代码，我对正在服务的 Lite CC Switch 执行了优雅重启。旧进程进入关闭状态后不再接受新请求，但 CC Switch 仍持续将请求发往本地 `15720`，于是请求收到 HTTP 503：`Lite CC Switch 正在关闭，暂不接收新请求。`

随后重启脚本报告的新进程没有持续运行，15720 一度连接失败。这次用户可见的 503 是部署时机和重启流程造成的，不是原始上游过载错误。新进程后来消失的具体原因没有足够日志证据，不能断定。

## 影响范围

- 受影响入口：Codex → CC Switch `127.0.0.1:15721` → Lite CC Switch `127.0.0.1:15720`。
- 用户看到的错误明确包含 `Provider: cct`、`model: gpt-6.1-sol`、`upstream_status: HTTP 503` 和 `service_shutting_down` 原因。
- 活跃 Codex 对话的一次请求被中断；在新 Lite 恢复前，通过该链路发起的请求无法正常使用。
- 本次调查没有修改真实供应商配置、API 密钥、Codex 配置或 usage 历史。
- 回退后服务已在本次核验时恢复。恢复状态及测试结果见“恢复与验证”。

## 事故前背景

原始故障发生于前一天。2026-10-22 约 23:49–23:50，供应商返回容量过载 `Our servers are currently overloaded. Please try again later.`，Lite usage 记录为 HTTP 503 / capacity。代理可能已转发上游 SSE 生命周期事件，随后遇到失败并中断下游，Codex 因而报告 `stream disconnected before completion`。

这与本次部署期间的 503 不同：

| 故障 | 直接来源 | 表现 |
| --- | --- | --- |
| 原始断流 | 上游供应商容量过载发生在 SSE 已开始之后 | Codex 报响应体解码错误/流未完成 |
| 本次部署中断 | Lite 在收到 `SIGTERM` 后停止接收新请求 | CC Switch 收到 `service_shutting_down`，HTTP 503 |

## 时间线

具体时间以本地日志和当时操作记录为准；未被日志精确记录的时间不作推测。

1. 原始会话通过 `15721 → 15720` 使用 `gpt-6.1-sol`。上游容量过载导致流式响应没有正常完成。
2. 为处理流式供应商故障，增加了 Responses 全量缓存、完成事件确认、心跳和自动故障转移分支，并添加/调整隔离测试。该版本曾通过 148 项测试及本地伪供应商到真实 Codex CLI 的协议验证。
3. 部署时运行 `./tools/lite-ccswitch/restart.sh 15720`。脚本向原 Lite PID `67757` 发送一次 `SIGTERM`。原服务开始排空已有连接并停止接受新请求。
4. 在新旧进程交接期间，CC Switch 仍向 `15720` 转发 Codex 请求。旧服务在关闭阶段返回 `service_shutting_down`，Codex 收到用户贴出的 HTTP 503。**这一步是本次可确认的中断直接原因，也是我在部署操作中造成的。**
5. 重启脚本报告新进程 PID `33010` 已启动。之后检查时，该 PID 已不存在，`15720` 和 `15722` 都没有监听进程；日志只保留服务启动信息，不能解释进程为何退出。
6. 按用户要求开始回退本次代码改动。回退代码语法检查通过，原有 SSE/优雅关闭和相关集成测试通过。
7. 第二次使用重启脚本时，脚本报告 PID `33931` 就绪，但健康检查随后仍无法连接。由此确认该脚本的一次性 ready 探测不足以证明进程在脚本退出后持续存活。
8. 改为在当前工作会话中以前台方式启动恢复后的 Lite，PID `34026`。主端口状态检查和经 CC Switch 的实际请求均成功。

## 因果分析

### 已确认的直接因果链

```text
对正在服务的 Lite 执行 SIGTERM
  → Lite 停止接收新请求并开始排空
  → CC Switch 仍把 Codex 请求发往 15720
  → Lite 按关闭状态返回 503 service_shutting_down
  → Codex 对话被中断
```

错误内容直接指向 Lite 的关闭状态，而非上游供应商响应。这是区分“功能代码缺陷”和“部署中断”的关键证据。

### 事故延长的原因仍未确认

重启脚本打印了新 PID 并短暂通过 `/api/auth/status` ready 检查，但随后进程消失。现有日志没有退出码、信号来源或异常堆栈，不能据此声称是缓存代码、配置、操作系统或命令执行器中的某一项导致退出。

可以确认的是，脚本的 ready 条件只证明某个时刻接口响应成功；脚本没有在返回成功后持续监测新 PID，也没有验证它在后续时间窗口内仍持有端口。短暂就绪和稳定运行被混为一谈，是验证流程的不足。

### 修改与事故的关系

本次添加的全量缓存改变了流式响应策略：每次 Responses 调用在上游完成前不会向 Codex 输出文字或工具调用。这是明显的用户体验改变，需要单独决策和验证。但用户贴出的 503 明确来自 Lite 收到 `SIGTERM` 后的关闭状态；没有证据表明缓存解析代码直接生成了该错误。

真正触发中断的是部署时重启在线代理，而现有链路没有在交接窗口暂停/缓冲新请求，也没有由 CC Switch 对这个本地关闭状态做短暂重试。我在没有验证无损交接和进程持续存活的情况下执行了部署，是此次事故的操作责任。

## 恢复与验证

回退遵循逐项撤销，而不是从其他目录复制较旧的 Lite 版本：

- 从本项目 `server.js` 撤掉 SSE 全量缓存分支、心跳和相应请求控制逻辑，恢复原有供应商尝试及错误处理路径。
- 从本项目 `lib/sse-stream.js` 撤掉新增的完整流缓存函数，恢复首包探测后即时转发。
- 撤掉为缓存行为新增的单测、集成测试及业务恢复、分组端口、粘滞路由测试适配。
- 保留回退前本项目已有的路由、断路器、SSE 首包探测和优雅关闭代码。
- 没有改写 `data/config.json`、`data/usage.jsonl`、Codex 配置或供应商密钥。

回退后检查结果：

- `node --check server.js` 与 `node --check lib/sse-stream.js` 通过。
- SSE/优雅关闭测试 19 项通过。
- 供应商故障转移、业务恢复、分组端口和粘滞路由集成测试 6 项通过。
- 2026-10-23 约 00:41 核验时，`15720 /api/status` 返回 HTTP 200，`running: true`，PID `34026`，活动连接数为 0；默认端口 `15720` 与分组端口 `15722` 均在监听。
- CC Switch 入口 `15721` 的非流式请求返回 HTTP 200 和 `PONG`；实际 SSE 请求返回 HTTP 200，观察到 `response.completed`，未观察到 `response.failed`。

PID `34026` 是在当前工作会话中以前台方式启动的。本次确认它正在运行，但没有验证它是否由 launchd 等系统服务托管，也没有验证系统重启后的自动恢复行为。

## 改进措施

### 已完成

- 按要求逐项回退本次功能修改。
- 以运行状态接口、监听端口和真实 `15721 → 15720` 请求确认服务恢复，而不是只依赖重启脚本的成功文字。
- 分开记录原始上游容量故障与本次本地关闭 503，避免把两个不同原因混为一谈。

### 后续部署需要补足

1. **避免交接空窗**：研究并验证 CC Switch 在短暂 `service_shutting_down` / 连接拒绝时的有限重试，或设计具备监听器接管/排队能力的部署方案。单纯先关旧服务再启动新服务，无法保证没有请求落入窗口。
2. **检查稳定存活**：启动脚本除检测 HTTP ready 外，还应核实 PID 仍存活且持有预期端口；通过连续健康检查窗口后才能报告成功。
3. **保留快速恢复路径**：启动失败或健康检查中断时，恢复到已知可用版本/进程，并再次验证代理入口，而非只验证本地子服务。
4. **先做隔离演练**：使用本机伪上游保持活动 SSE，同时施加新请求、发送关闭信号并启动替代进程，验证已有请求排空、新请求的行为和失败恢复。
5. **把行为验证与部署验证分开**：单测和协议集成测试证明请求逻辑；重启、端口接管和进程生命周期测试证明运维流程。两类检查不能互相替代。
6. **上线前确认产品取舍**：全量缓存可以隔离失败供应商的部分输出，但会延迟每次响应的可见输出；不要仅凭测试通过就把这个交互变化部署到正在使用的服务。
