# Codex 流式断流问题：目标与分析

## 记录范围

本文记录本次最初要解决的问题、确认到的故障链路、预期目标、已尝试方案及方案边界。它聚焦 Codex 的流式断流；后续重启期间发生的 503 事故详见[独立复盘](2026-10-23-LiteCCSwitch修改部署503事故复盘.md)。

## 一句话说明目标

当 Codex 使用流式 Responses API 时，如果当前供应商在响应尚未安全提交给 Codex 前发生过载、断连、EOF 或超时，Lite CC Switch 应及时尝试下一家可用供应商，尽量让原请求正常完成，避免 Codex 收到半截 SSE 后报 `stream disconnected before completion`。

目标是提高可恢复故障下的请求成功率，不是承诺在所有供应商都不可用、请求无效、客户端取消或重试预算耗尽时永远不报错。也不应让同一个工具调用被执行两次，或把失败供应商的响应和备用供应商的响应拼成一条看似完整的流。

## 用户看到的现象

受影响的 Codex 会话信息：

- Codex CLI：`0.163.0`
- 模型：`gpt-6.1-sol`
- 模型供应商标识：`cc-switch-official`
- 会话 ID：`01a060d0-0a27-76f3-ba32-307d28d113f9`
- 报错：`stream disconnected before completion: Transport error: network error: error decoding response body`

实际转发链路为：

```text
Codex → CC Switch 127.0.0.1:15721 → Lite CC Switch 127.0.0.1:15720 → 上游供应商
```

因此，Codex 的错误是链路末端观察到的响应不完整；要区分是 CC Switch 本地拒绝、Lite 代理中断，还是上游供应商自身失败，不能仅根据 Codex 的报错文字判断。

## 已确认的最初诱因

2026-10-22 约 23:49–23:50 的故障记录显示，上游供应商在 SSE 生命周期事件之后返回 `response.failed`，内容为：

```text
Our servers are currently overloaded. Please try again later.
```

Lite 的 usage 记录将该次失败标记为 HTTP 503 / capacity。故障会话后来于约 23:58 因另一次供应商切换恢复；该恢复不是本次自动故障转移代码带来的结果。

这里要区分两个事实：

- 上游容量过载是原始故障的触发原因。
- Codex 报“响应体解码失败/流断开”，是因为代理在下游响应已开始之后，又遇到了上游失败，没能向 Codex交付完整、可解析的终止结果。

## 代理为何会中断流

原来的流式路径会先读取 SSE 前导并做结构探测，然后将流交给下游实时转发。生命周期事件可以证明上游已开始响应，但不代表该响应最终一定成功。若代理已经把 `response.created`、`response.in_progress` 或正文事件写入 Codex 的 HTTP 响应，之后才读到 `response.failed`、连接断开或 EOF，就无法再撤回已发字节，也无法把另一个供应商的独立 Responses 流安全地接到后面。

这时代理只能让本次响应以失败结束。若底层连接直接被销毁，CC Switch/Codex 可能看到截断的 SSE 或不完整响应体，最终产生 `stream disconnected before completion`。已经提交下游的响应不等同于“已经输出可见文字”：即使只有生命周期元数据或工具调用参数，切换也可能污染响应 ID、会话上下文或触发重复工具执行。

实现位置可参考 [server.js](../../server.js) 的供应商尝试与响应转发逻辑，以及 [lib/sse-stream.js](../../lib/sse-stream.js) 中的首包探测和 SSE 读取逻辑。

## 成功标准

若继续实现这项能力，应将目标拆成可验证条件：

1. 第一家供应商在发送任何会影响客户端状态的 SSE 内容前返回容量错误、连接错误、无完成事件的 EOF 或超时：代理切到下一家，并重放同一请求。
2. 第一次失败的响应 ID、正文和工具调用不会混入备用供应商的响应。
3. 备用供应商成功时，Codex 收到一条完整的 Responses 流并观察到 `response.completed`。
4. 客户端取消后立即停止尝试，不额外向供应商发请求。
5. 所有供应商均失败、请求不可重试或整体预算耗尽时，仍返回可诊断的明确失败；系统不能伪造 `response.completed`。
6. 真实 CC Switch `15721 → Lite 15720` 路径、工具调用、`previous_response_id`、慢响应、长输出及会话粘滞均通过验证。

## 曾尝试的实现及取舍

为使失败供应商的部分 SSE 不泄漏给 Codex，曾增加“单次 Responses 请求完整缓存”路径：Lite 在内存中读取并解析上游流，只有收到 `response.completed` 才开始转发；中途发生可重试错误则尝试下一家。等待期间发 SSE 注释心跳维持连接。实现还设置了缓存大小上限、空闲超时、整次请求截止时间，并在客户端取消时中止上游。

这样做解决了一个协议难点：备用响应不会与首家供应商的半截响应混合。但是它带来明显体验变化：每次 Responses 调用的文字、推理和工具调用都要等到本次响应完成后才显示。它也扩大了改动范围，需要验证请求重放语义、usage 记录、断路器、sticky routing、错误正文、异常退出和资源回收。

这套实现曾在隔离环境中通过 148 项回归检查，并用本地伪供应商验证真实 Codex CLI 可完成“首家在部分输出后失败、备用供应商返回成功”的流程。那只能说明隔离测试场景通过，不能证明生产部署无中断，也不能替代正式 CC Switch 路径和运行生命周期验证。后续部署导致的 503 属于独立的重启事故，详见另一份复盘。

## 当前状态与已知边界

按用户要求，完整缓存逻辑和相应测试适配已逐项撤回，恢复本项目此前的 SSE 首包探测和实时转发。回退后原有 SSE/优雅关闭测试 19 项通过；供应商故障转移、业务恢复、分组端口和粘滞路由集成测试 6 项通过。实际 CC Switch 入口测试中，非流式请求返回 `PONG`，SSE 请求返回 HTTP 200 并观察到 `response.completed`。

当前实现能在供应商错误发生于下游响应提交之前按既有策略尝试其他供应商。若已经有部分响应提交给 Codex 后才发生错误，仍不能保证透明切换；此时用户仍可能看到不完整响应或需重新发起请求。回退恢复了原来的即时输出体验，但没有完成“任意时点的供应商失败都不向 Codex 报错”这一更强目标。

## 后续方案选择

后续设计应先明确两种互有代价的路线：

- **优先实时输出**：只在供应商内容尚未提交前故障转移。提交之后不拼接第二家响应；向客户端返回符合协议的明确失败，或由调用方在确认安全后重发整轮请求。需特别检查工具副作用和会话上下文。
- **优先透明切换**：缓存足够多的响应，在确认整次 Responses 成功后再转发。需要接受输出延迟，并对响应最大大小、超时、取消、并发内存占用和工具调用做严格测试。

无论选哪条路线，都应先通过不涉及真实供应商的故障注入测试，再用隔离的本机 Codex/CC Switch 链路验证，最后在可快速恢复的部署流程中上线。应将“请求行为正确”和“部署后进程持续存活”作为两个独立验收项。
